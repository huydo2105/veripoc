# Trusted Foundry fixture worker (Issue #5)

Build the image from this repository: `docker build -f infrastructure/docker/foundry-worker.Dockerfile -t veripoc-foundry-worker:issue-5 .`. Run `npm run test:worker`, `bash workers/sandbox/isolation.sh`, then `npm run run:worker` on a Linux host with Docker. CI runs those commands. The Windows machine used for development has no running Docker daemon, so local unit and Foundry results are separate from container evidence.

The image compiles the checked-in Solidity fixtures and fixed harness at build time. Its runtime has no host source mount, no network, no inherited RPC credentials, a read-only root, a non-root UID, dropped capabilities, no-new-privileges, PID/CPU/memory limits, and bounded writable tmpfs. The controller locks to the inspected image ID, selects only two fixed test names, and limits each run to 30 seconds and 64 KiB of output. It emits `reproduced` for the vulnerable fixture and `not_reproduced` for the patched fixture only when their trusted invariant tests pass. A failure is `tool_error`; a timeout is `inconclusive`. The input hash covers the compiler settings, source, tests, harness, and Dockerfile.

The local fixtures use no fork RPC. A future fork job must prefetch and verify a pinned state snapshot before the network-isolated run; this worker does not accept a remote fork URL. The Foundry v1.9.0 archive is SHA-256 pinned. The Debian base image and apt packages are not digest pinned; record and review the resolved image ID before relying on reproducibility across builds. Docker host, daemon, image registry, and trusted harness remain in the trusted computing base. Do not feed untrusted submissions or unreviewed image builds to this development workflow.
